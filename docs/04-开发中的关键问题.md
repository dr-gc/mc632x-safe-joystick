# 开发中的关键问题与解决过程

## 1. 屏驱动选型与实际配置不一致

最初按 AT070TN94 屏配置为 800×480 RGB，但屏上只显示黑白条纹，`media_info -r vou` 却显示 VOU 侧完全正常（FrmRevCnt = FrmDisCnt，零丢帧）。

用 strings 检查 liblcm_module.a，发现库内含四种屏驱动，mol_lcm_probe 自动探测到了 lcm_id=1（MCU ST7796S 320×480），而配置项并未真正生效——驱动选择逻辑封在厂商预编译库中。

由于库没有源码，最终对 libvou.a 做二进制补丁，让 read_tab_index 返回 1 走 RGB 分支，随后 mol_lcm_scan 正确识别为 rgb_AT070TN94_800x480。

这次调试让我认识到，媒体配置不能只看 menuconfig 里的选项，必须用运行期状态和实际出图交叉核对。

## 2. 第二路摄像头无法启动

开启 VIDEO_GRP1 后，第二路 ISP 报 -3003 错误，demo 直接退出。

排查发现 Sensor1_Kconfig 里根本没有 CV2005 选项——厂商只给 Sensor0 配了这一款，而双摄还必须开启 CONFIG_SENSOR_SLAVE_MODE 做主从同步，否则 MIPI 时序无法对齐。

补充 Sensor1_Kconfig 的 CV2005 配置项并开启主从同步后，日志出现 Start Sensor[1] sync，两路 RTSP 同时建立。

## 3. 内联模型被当作堆内存释放

为摆脱文件系统依赖，用 .incbin 把人形模型编进固件 .data 段。运行即崩溃。

原因是 nna_config.c 在任务创建后无条件调用 SDK_FREE_PTR 释放模型内存——这个逻辑对原版是正确的，因为模型由 readFile 分配在堆上；但内联模型位于固件静态区，释放它属于非法操作。

为此新增 mem: 前缀机制与 model_from_mem 标志，标记为静态模型时跳过多处 free 调用。这是新增功能必需的配套改动，不是对原有逻辑的修补。

## 4. 视频链路被 Python 解码拖慢

最初 Python 拉取 RTSP 后解码为 RGB，再用 PIL 编码成 JPEG 推给浏览器，视频只有 10.5 fps。

测量发现瓶颈不在编解码速度（PIL 单帧编码上限约 115 fps），而在 GIL 竞争——两路视频、手部检测和 Flask 四个线程互相抢锁。

改为两条 ffmpeg 管线直接输出 MJPEG 字节流，Python 只按 JPEG 边界切帧，完全不做解码重编码；手部检测另起一路低分辨率 rawvideo。视频采集从 10.5 fps 提升到 55 fps。

## 5. 手写规则判断握拳不可靠

最初用手写几何规则识别握拳：指尖到掌心的距离除以掌宽，小于阈值即判定握拳。

实测发现半张的手也会被判成握拳，导致反复误触急停。进一步检查还发现配对写错——中指指尖对的是掌心本身（9 号点既是掌心又是中指 MCP），距离比算出 229133 倍。

改用预训练 MLP 后，归一化方式以手腕为原点、按手部尺寸缩放，4450 条真实样本准确率 96.52%。更关键的是误判方向变了：从误触发急停变成偶尔漏报，对安全功能来说这是正确的取舍。

## 6. 画布镜像后骨架消失

为符合直觉，两路画面做了左右镜像（transform: scaleX(-1)），但坐标映射也必须同步翻转，否则骨架与手错位。

给坐标映射加上 mirror 参数后，骨架反而完全不显示了。检查浏览器控制台发现 drawZone 里的 ctx.arc 抛出异常：镜像后计算工作区宽高时 zx2 - zx1 变成负数，半径随之为负。

改为用 Math.min / Math.max 归一化边界，并给半径下限保护，同时把两块画布的绘制分别包进 try/catch，避免一处异常中断整体绘制。

## 7. 串口设备名漂移

板子换 USB 口后，串口从 /dev/ttyUSB0 变成 /dev/ttyUSB1，后端硬编码的路径失效，界面持续显示 UART OFFLINE。

改为用 glob 扫描 /dev/ttyUSB* 取第一个，重启后端即自动跟随。这类硬件枚举顺序的问题不应写死。

## 8. 检测阈值调参的两难

MediaPipe 默认检测阈值 0.5，手稍远离镜头就丢失，实测 20 次采样只有 1 次检出。

把三个阈值全部降到 0 时，MediaPipe 内部断言失败直接崩溃（Check failed: min_similarity_threshold() > 0.0）；全部设为 0.01 又引入大量背景误检，手势判定开始乱跳。

最终只放宽 detection 到 0.15，presence 和 tracking 保持 0.35 / 0.30，检出率从 1/20 提升到 20/20 且无误检。

## 9. 心跳与看门狗的两难

执行端配有 3 秒断流看门狗，用于上位机崩溃时自动刹车。但若只在方向变化时下发指令，小车走 3 秒后就会被看门狗误判超时刹停。

改为每 0.5 秒重发当前指令：方向变化时立即更新，未变化时按心跳重发。这样既保证控制连续，又保留了上位机真正失联时的刹车兜底。

## 10. 已知但未解决的硬件问题

板端 VOU 链路已完全打通：驱动识别正确、时序参数正确、通道使能、帧计数零丢帧，但屏上仍不显示画面。背景色测试显示白色与黑色能正常输出，红色与绿色不显示，说明 RGB 数据线仅部分导通。

软件侧已穷尽排查，判定为排线或面板数据线层面的硬件问题。本次展示不依赖该屏，分析结果统一在 PC 端呈现。

视频源帧率同样受限于 CV2005 驱动：配置为 1080P15，VPU 实测输出 6.55 fps，改 1080P30 配置生效但输出不变，改 720P 各帧率均报 -3003 不被支持。已排除算力、丢帧、溢出等因素，判定为 Sensor 与 MIPI 时序层面的固有限制。
